### 2.2 How theming works today — light/dark only, NO accent customization

- `theme: 'light' | 'dark'` in the store; `hasCustomTheme` means only "user overrode device sync" (page.tsx device-sync effect follows `prefers-color-scheme` unless `hasCustomTheme`).
- Settings → Appearance offers exactly three choices: Chalk (light), Graphite (dark), System (device). `ThemeToggle` is a light/dark switch. There is **no accent-color preset, no custom accent input, no accent token override** anywhere in store, Settings, or CSS.
- The `--accent` CSS variable + Tailwind `accent.*` aliases already exist, so a future accent system can be built by overriding `--accent`/`--accent-dim`/`--accent-glow` per theme — but no such mechanism, UI, persistence key, or contrast safeguard exists today. `uiPreferences` holds only: `gamificationEnabled`, `coachEnabled`, `showHabitMatrix`, `weeklyTargetDays` (null/0/2–6), `language` (en/hi), `textScale` (normal/large/xlarge), `healthConnectEnabled`, `showMuscleVolume`. **No Simple/Detailed mode, no dashboard card visibility/ordering, no accent preference exists.**
- Typography: Inter body; `display` family in Tailwind points at `--font-sans` (Inter), so the loaded Barlow Condensed (`--font-display`, `preload: false`) is **dead weight** — headings do not use it. Sizes: `3xs` 10px/14px (comment in config: it was used in 100+ places before being defined and silently fell back), `2xs` 10.4px, `label` 12px, `body` 14px, `title` 17px, `display` 32px. Mono: JetBrains Mono / Fira Code (not loaded via `next/font` — falls back to system mono).
- Shared classes in `globals.css`: `.card` (rounded-2xl, border, `p-4 sm:p-5`), `.card-elevated`, `.btn-primary/.btn-secondary/.btn-outline/.btn-ghost/.btn-danger/.btn-circle`, `.card-title`, `.modal-overlay` (+ `-centered`), `.modal-content` (bottom sheet on mobile: `rounded-t-2xl`, `max-w-[520px]`, `max-h-[90vh]`), `.stepper-btn`, `.segmented-control` (used by Meals/Progress — class defined in globals, verify before reuse). Animations: 4 Tailwind keyframes (`fade-in`, `slide-up`, `scale-in`, `tab-enter`, 0.2–0.25 s). Reduced motion: one `@media (prefers-reduced-motion: reduce)` block in `globals.css:387` + `ExerciseDemo.tsx` freezes its animation on the first frame. Focus: global `:focus-visible` rule + `Button.tsx` focus-visible rings; inputs are forced to 16px to prevent iOS/Android auto-zoom.
- Spacing: no spacing-token scale beyond Tailwind defaults + ad-hoc `space-y-*`/`p-*` per component. Radii: cards/modals/inputs consistently `rounded-2xl`/`rounded-xl`; no central radius token.

## 3. Navigation & information architecture (as built)

- **Shell:** single-page client app. `page.tsx` renders by `activeTab`: splash (hydration) → onboarding (no profile) → tab views. A fixed 4-destination bottom nav: **Today** (`home`), **Train** (`workout`), **Progress** (`progress`+`prs`), **Fuel** (`meals`). Profile and Settings are full views reached contextually, **not** bottom tabs: avatar → Profile → gear → Settings; Today header also has a Settings gear (added by PR #41) and a notifications bell. `TabId` = `home | workout | progress | meals | prs | profile | settings`.
- **Sub-navigation:** Progress has 5 sub-tabs (`overview | strength | prs | bodyweight | training`); Train has 2 (`plans | history`, persisted as `lastTrainSubTab`); Fuel has 3 segments (`today | meals | macros`); PRs render inside Progress as the `records` view and also via TabId `prs`.
- **Routing mechanics:** `src/lib/navigation.tsx` (473 lines): URL deep links (`?tab=` + `?sub=`, `today` alias for `home`), a back-handler stack with per-modal registration (`useModalA11y` + `registerBackHandler`), persisted `lastActiveTab`/`lastProgressSubTab` (refresh/relaunch restores the tab instead of resetting to Home), service-worker `NAVIGATE_TAB` messages, and a `TabGuardBanner` for guarded tabs.
- **Code splitting:** Home is statically imported (first paint); Progress, Workout, Meals, Profile, Settings, ImportProgramModal are `next/dynamic` with `ssr: false` and `TabSkeleton` fallback — a documented 2 GB-phone parse-cost decision (old single chunk ~1.1 MB). Tab switches animate with `animate-tab-enter` keyed by `activeTab`.
- **PWA:** `public/manifest.json`, `public/sw.js` (`CACHE_NAME = 'ascend-v2.0.0-cache'`, static name; navigation = network raced against a 3 s timeout with cache fallback, assets stale-while-revalidate — **this is the known stale-shell mechanism**: a returning browser can be served a previous build's shell even from a fresh link; later phases must not rely on the alias alone for verification), `public/theme-init.js` (no-flash theme), `ServiceWorkerRegister`, `public/.well-known/assetlinks.json`.
- **App shell width:** pages use `max-w-md mx-auto px-5` (448 px centered column) with `pb-24` clearance for the bottom nav; modals cap at 520 px. Desktop is a centered mobile column, not a distinct desktop layout (see Top Problem #6).

## 5. Ten traced flows (Phase 0.3) — implementation path + fragility notes

All flows traced in code (`page.tsx` shell → view → store → persistence/sync). Fragility = a state transition that can lose data, confuse, or silently fail — not a styling complaint.

1. **New user onboarding.** Splash (hydration) → Welcome → Create account (email/password, validated) or Login (email/Google/Apple/OTP) or guest path via Goals → Goals → Experience → Schedule (days + injury dropdown) → Details (metrics + diet) → Plan offer (accept/skip) → tabs. State: `Onboarding.tsx` local `currentScreen` state machine + `?screen=` URL param override; profile written to store on completion. Fragility: (a) the screen machine is local component state — a refresh mid-onboarding restarts it unless the URL param or stored partial profile rescues it (verify in Phase 1); (b) guest vs account paths fork at Welcome but converge silently — a guest who later links Google must not lose local data (sync engine merges on sign-in; verify the merge direction in Phase 1).
2. **Returning user opens the app.** `theme-init.js` → hydration splash → `persist.hasHydrated()` → lastActiveTab restored (not Home) → tab view renders; device-theme sync applies unless `hasCustomTheme`. Fragility: (a) two hydration signals exist (`_hasHydrated` splash fallback vs true `persist.hasHydrated()`) with an explicit comment that the fallback can fire before persisted state merges — theme effects must wait for true hydration or the device theme overwrites the saved theme (already guarded in `page.tsx`, but any redesign touching theme effects must preserve the guard); (b) SW stale shell can serve an old build (see §3).
3. **Start / resume workout.** Plans list → Start plan (pre-fills logger) or blank logger → ActiveWorkoutScreen fullscreen (`isModalOpen`) with session start time; or resume via Today's workout card / active draft (`activeWorkoutDraft`, auto-saved to localStorage) / pause-and-save-draft. Fragility: (a) two entry surfaces (logger compose vs fullscreen perform) share the draft — a redesign that merges them must not break draft recovery; (b) `lastTrainSubTab` persistence can return the user to History when they expected Plans after a resume (minor).
4. **Record / edit sets.** ActiveWorkoutScreen: Beginner mode (one set at a time: weight/rep steppers, add/remove set) or Advanced mode (full multi-set table: per-set weight/reps/skip/complete, RPE/RIR, set types); change-exercise autocomplete; crowded-gym toggle; rest timer (floating button, effect-driven); voice logger as alternate input. State: local component state + auto-save to localStorage (`activeWorkoutDraft`); save only on Finish. Fragility: (a) edits live in component state until Finish — a crash/close before Finish relies entirely on draft recovery (verify draft restore coverage in Phase 1, incl. the "interrupted user" persona); (b) rest-timer effect + set-complete transition state are timing-sensitive (Screen 13 transition state) — redesign must not re-time them.
5. **Finish workout + review.** Finish → `addWorkout(entry)` → clear draft → post-workout summary (duration, exercises, sets, volume, genuine PRs) → `PostWorkoutTakeModal` ("Vs your block") → `PlanVsActualReview` / block debrief where applicable → back to Train/Today. Fragility: (a) finish computes duration from `sessionStartTime` with fallback to `durationMinutes`/`durationSeconds` — clock skew across pause/resume is a known edge (verify in Phase 1); (b) PR counting on finish must use the same derivation as PRsPage (single source — verify no duplicate PR logic in the summary path).
6. **History + progress exploration.** Train History → `WorkoutDetailsView` modal; Progress sub-tabs (overview/strength/records/body/training) → charts, heatmap, muscle volume, PRs, photos; `?tab=progress&sub=` deep links. Fragility: (a) ProgressPage derives everything from store arrays (no separate analytics store) — large histories re-derive on every render (perf note for Phase 9, not a correctness bug); (b) sub-tab label mismatch (code vs UI copy, §4.5) can break deep-link expectations.
7. **Nutrition record / review.** Fuel Today → Scan (LLM, loading → review → save) / Add manually (form + autocomplete + portion memory) / Barcode (ZXing → OFF → form) / Voice / NL text (`/api/ai/parse-meal`) → "What you ate today" + targets; Meals tab = history; Macros tab = breakdown; goals form edits targets; pinned foods quick-add. Fragility: (a) scan result review is the honesty boundary (exact vs estimated labels) — redesign must not collapse the distinction; (b) portion memory (`userPortionPreferences`) overrides hardcoded pinned defaults silently — the UI must show which value is a memory vs a default (currently unclear — Phase 1 probe); (c) scan/barcode/voice are three async inputs into one meal list — duplicate-submission guards live per-modal (verify in Phase 1).
8. **Settings / personalization change.** Settings (4 sections, sticky chips) → toggle/pick → `setUiPreferences` / `setTheme` / store setters → zustand-persist (localStorage) → Supabase sync where the field is synced (theme + uiPreferences travel in the sync payload; verify per-field sync coverage in Phase 1 — not every preference is necessarily synced). Fragility: (a) theme changes race device sync unless `hasCustomTheme` is set with the change (the `setTheme(theme, isCustom)` two-arg form — redesign must keep passing `isCustom=true` for user picks); (b) text-scale changes root font size (whole UI scales, incl. 10px labels — verify no layout breakage at `xlarge` in Phase 1); (c) language switch swaps the entire 2,700-line dictionary at runtime — missing keys fall back to… (verify fallback behavior in Phase 1; `StringKey` typing suggests compile-time key safety for `en`, not runtime safety for `hi`).
9. **Offline / loading / sync problem.** `navigator.onLine` → offline banner + "Offline Gym Mode" modal → local-first operation continues (store is local; sync engine queues) → reconnect → sync engine reconciles (`sync.ts` + `reconcile.ts`, tombstones for deletes, `extras` JSONB for unmapped planned-workout columns) → Settings shows sync status (synced/syncing/idle/local-only) + Sync now. Fragility: (a) sync covers 6 tables on master (profiles, personal_records, workouts, meals, body_metrics, planned_workouts) — coach data, challenges, habits, photos, and several preference fields are local-only (verify the exact synced-field list in Phase 1; do not promise cloud backup for local-only data in UI copy); (b) multi-tab writes are coordinated by `tab-leader.ts` — redesign must not add a second writer path; (c) the SW stale-shell issue (§3) is the most user-visible "sync-like" failure (old UI after deploy) and is not a data-sync bug.
10. **Switch / sign-out account.** Profile/Settings → Sign out (option: keep vs clear local data) → guest state (local profile retained or cleared per choice) → onboarding or tabs; account switch = sign out + sign in (no multi-account switcher exists); delete account = token-mailed flow + purge + API. Fragility: (a) sign-out-with-clear is destructive and must keep its confirmation + exact semantics; (b) the Supabase URL hop during OAuth is structurally mandatory on the free tier (config requires `*.supabase.co`) — no code-only fix exists for hiding it (prior audit finding, restated here so Phase 3 does not re-promise it); the only full fix is a paid custom domain (user decision, $25/mo Pro); (c) guest→cloud merge on sign-in must not duplicate workouts/meals (reconcile logic — verify idempotency keys in Phase 1).

## 7. Top 10 UI/UX problems for later phases (ranked, with evidence)

1. **Today is a 14-section stack, not a daily starting point.** HomePage renders header + workout card + nutrition + readiness + level + athlete model + weekly review + quick actions + hydration + coach notes + steps + habit matrix + challenge + quote (§4.3). PR #41 already collapsed the coach cluster, but the page still answers "everything" before "next action." Evidence: `HomePage.tsx` § comments 1–8c + quote; 1,459 lines. Phase 3 must decide the above-fold set (today's workout + next action + one supporting signal) and demote the rest — without deleting any capability.
2. **Settings is discoverable only via icons, and Profile vs Settings split the same concerns.** Bottom nav has no Settings/Profile; entry is an unlabeled avatar and a header gear (§3, §4.7). Account-ish rows live in both Profile menu and Settings §1. Evidence: `page.tsx:386` (4 tabs), `HomePage.tsx:570,579`, `ProfileView.tsx:181`, `SettingsView.tsx:369`. Phase 3 Q8 (Profile vs Settings) is the highest-leverage IA decision.
3. **No accent theming, no Simple/Detailed mode, no dashboard personalization exist — the brief's three headline features are all greenfield.** Theme = light/dark/system only; `uiPreferences` has no accent, density, or card-order keys (§2.2). The existing toggles (gamification/coach/habit-matrix/muscle-volume) are the only personalization precedent. Phase 6 must build all three on the `--accent` token system + `uiPreferences` persistence, with contrast safeguards — and must not redefine semantic colors (§2.1).
4. **Duplicated surfaces with unclear canonical paths.** Diet preference (Fuel + Settings + Onboarding, shared picker — good), schedule (Onboarding + Settings editor), habits (Today quick-add + Fuel), scan entry (Today + Fuel), notifications (bell + Settings row → same ReminderCenter), auth (AuthModal Google-only vs engine 5 methods), PRs (Progress sub-tab + TabId). Some duplication is deliberate (fast path vs full path); some is accidental drift. Phase 3 must classify each pair as canonical-vs-shortcut and make labels identical.
5. **Active workout is powerful but dense, and its two modes are undiscoverable.** Beginner (one set at a time) vs Advanced (full table) already exists (§4.4) but the mode switch lives inside the workout tools menu (`ActiveWorkoutScreen.tsx:1962`), and the screen is 4,069 lines with steppers, RPE/RIR, set types, crowded-gym, form cues, and a floating rest timer competing for attention. Phase 5 must make the mode obvious, protect the one-hand hierarchy (exercise → set → values → previous → next action), and keep the rest timer from covering controls.
6. **Desktop is a stretched mobile column, not a layout.** `max-w-md mx-auto` everywhere (§3); no desktop grid, no two-pane progress/workout view, no distinct tablet behavior. The brief's responsive targets (320–1440 px) will expose this immediately. Phase 8 must design a real ≥1024 px composition, not just wider gutters.
7. **Modal layer is ~36 components with per-page open-state and nested stacks.** No shared modal manager; each page owns its booleans + back-handler registrations; nested modals (selector in logger, detail in history) rely on the stack-aware trap in `use-modal-a11y`. Any component-system work (Phase 4) must preserve stack/Escape/back-button semantics or regressions will appear in exactly the flows users trust (logger, history detail, scan review).
8. **Charts are hand-rolled and label-fragile; metric naming drifts.** No chart library; `ProgressChart`/`WorkoutHeatmap` render axes/units/labels by hand, and sub-tab names differ between code and UI copy (§4.5). Measured vs estimated (e1RM) distinction, time-range clarity, and empty-state charts are all Phase 6 risks. Do not restyle charts without re-verifying every axis, unit, and date label against real data.
9. **Semantic color + text-scale + tiny-label debt.** Success == muted (§2.1); `text-3xs` (10px) is used pervasively for labels/meta (defined only after it was already used in 100+ places); `textScale` `xlarge` scales the whole UI including 10px labels (breakage unverified at 390 px and at `xlarge`). Phase 8 must audit contrast (all themes incl. future accents), minimum touch targets, and the `xlarge` layout before claiming AA.
10. **First-run and empty states are the weakest product moments.** Onboarding is 9 screens ending in a plan offer (skip must stay obvious); a new user lands on a Today page whose sections are mostly empty/conditional (readiness, athlete model, review, steps, challenge all depend on history); Fuel/Progress empty states are per-screen conditionals, not a shared pattern. The brief's "strong opening experience" must be built from the existing single photo asset or pure typography — previous redesign illustrations were rejected by the user, so decorative imagery must not be assumed wanted (see §8).

## 8. Phase 1 seed direction — where simulation attention belongs most
