## Scope

1. SEC-20 API floor — `src/middleware.ts` allowlist vs. the on-disk route set, 404 behaviour, per-IP ceiling.
2. Rate limiting / fail-closed (SEC-02) — `src/lib/rate-limit.ts`, `src/lib/ai-quota.ts`, and all five AI routes (coach, coach-chat, parse-meal, parse-voice, scan-meal): ordering relative to provider calls.
3. Coach-chat hardening — body/message/history caps, pre-provider safety scan, output guardrail scan.
4. Auth & account deletion — signed-token/nonce verification, SEC-19 fail-closed secret handling, replay protection.
5. Headers / CSP — `next.config.js`, `/api/csp-report` sink. `'unsafe-inline'` in `script-src` is a recorded user decision (SEC-16) and was **not** re-litigated; only its wiring was verified.
6. Secrets & dangerous sinks — grep over `src/` and `scripts/`.
7. Supabase client usage — anon vs. service_role placement, `NEXT_PUBLIC_` exposure, `'use client'` boundary.
8. Dependency versions — from `package-lock.json` / `package.json` only (no `npm audit`; endpoint blocked in this sandbox).

## Method

- Direct reads of every file named in scope, with line-level citations.
- Programmatic set comparison of the middleware allowlist against `find src/app/api -name route.ts` (13 routes).
- Ripgrep sweeps for secret patterns (`sk-…`, `AKIA…`, `BEGIN PRIVATE KEY`, `AIzaSy…`, `gsk_…`, `sk-or-…`, `ghp_…`, hardcoded `key/secret/password/token = "<16+ chars>"`) and sinks (`dangerouslySetInnerHTML`, `eval(`, `new Function`, `.innerHTML =`) over `src/` and `scripts/`, with test-fixture hits separated from shipped code.
- Lockfile inspection via a JSON parse of `package-lock.json` (`packages` map), not text search.

### 2. Rate limiting / fail-closed (area 2)
- **Fail-closed core:** `src/lib/rate-limit.ts:243-268` — if the distributed (Supabase RPC) limiter is configured but fails, a `failClosed` call throws `RateLimitUnavailableError` (lines 250-253); if it is **not configured at all** (service key absent, SEC-02), a `failClosed` call also throws (lines 255-267) instead of degrading to per-instance in-memory counting. Non-`failClosed` callers fall back to in-memory by documented design (line 271).
- **All five AI routes fail closed and limit before providers**, in the order per-minute IP limit → per-actor daily quota → body parse → provider call:

  | Route | Per-minute limit (`failClosed: true`) | Daily quota | Body cap | Provider call |
  |---|---|---|---|---|
  | `src/app/api/ai/coach/route.ts` | :97-106 (25/min) | :121 | :142 (64 KB) | :273 |
  | `src/app/api/ai/coach-chat/route.ts` | :47-57 via `enforceLimit` (10/min); daily chat cap re-check :102-111 | :84 | :115 (64 KB) | :161 |
  | `src/app/api/ai/parse-meal/route.ts` | :20-27 | :42 | :62 (4 KB) | :113 |
  | `src/app/api/ai/parse-voice/route.ts` | :14-21 | :36 | :56 (4 KB) | :95 |
  | `src/app/api/ai/scan-meal/route.ts` | :35-42 (20/min) | :57 | :99 (multipart 12 MB) / :158 (JSON 16 MB) | :285 |

  Every route maps `RateLimitUnavailableError` to the shared 503 response (`rateLimitUnavailableResponse`, `src/lib/server-security.ts:193-202`) and `AiActorAuthError` to 401.
- **Guest quota is IP-only (SEC-01 holding):** `src/lib/ai-quota.ts:89-100` — the guest key is `sha256(server-observed IP)`; the User-Agent no longer participates, and no body/query/cookie/client-header identity is read anywhere in the module. Signed-in quota is keyed by the Supabase-verified uid only. Caps: 50/day signed-in, 10/day guest by default (`src/lib/ai-quota.ts` `DEFAULT_AI_QUOTA_SIGNED_IN_DAILY = 50`, `DEFAULT_AI_QUOTA_GUEST_DAILY = 10`), enforced via `checkRateLimitForKey(..., failClosed: true)` at `src/lib/ai-quota.ts:213-218`. Present-but-unverifiable Bearer tokens throw `AiActorAuthError` (fail closed, no guest downgrade).
- **Fleet backstop:** global 500/day cap inside the provider layer (`src/lib/ai-provider.ts`, `DEFAULT_AI_DAILY_GLOBAL_CAP = 500`, `assertAiDailyBudget`). Its internal check uses `failClosed: false` — acceptable as written because every current caller route has already failed closed on limiter outage before reaching the provider layer (rationale stated in the module); it would become a gap only if a future caller reached the provider layer without a fail-closed route check.
- **Non-AI routes** (barcode, feedback, csp-report, notifications, delete-account at `src/app/api/auth/delete-account/route.ts:109-114`, 5/15 min) use the same limiter **without** `failClosed` and therefore degrade to in-memory counting on backend failure. This matches the documented design in `rate-limit.ts` and is recorded here as a known residual, not a new finding: the expensive/cost-bearing surface (AI) is the fail-closed one.

### 3. Coach-chat hardening (area 3)
- **Body cap on streamed reads:** `readJsonBodyWithLimit(req, COACH_CHAT_BODY_LIMIT)` at `route.ts:115`, with `COACH_CHAT_BODY_LIMIT = 64 * 1024` (`src/lib/coach-chat.ts:35`). The underlying reader is genuinely streaming — `src/lib/server-security.ts:100-144` reads chunk-by-chunk, cancels the stream past the cap, and throws `RequestBodyTooLargeError` (→ 413 at `route.ts:196-198` approx.).
- **Message/history caps:** message 1–2000 chars enforced at `route.ts:117-120` (`COACH_CHAT_MAX_MESSAGE_CHARS = 2000`, `coach-chat.ts:25`); history sanitized to ≤10 turns (`COACH_CHAT_MAX_HISTORY_TURNS = 10`, `coach-chat.ts:27`) with each turn sliced to 2000 chars (`coach-chat.ts:440`) — see SEC-R8 for the first-vs-last selection quirk; `contextText` sliced to 12,000 chars and `evidence` to 30 string entries (`route.ts:126-131`). Reply truncated to 1500 chars (`COACH_CHAT_MAX_REPLY_CHARS`, `coach-chat.ts:21`; `truncateReply` at `coach-chat.ts:421-424`, applied at `route.ts:180`).
- **Per-IP caps:** 10/min (`COACH_CHAT_MINUTE_CAP = 10`, `coach-chat.ts:29`) and 30/24 h chat-specific (`COACH_CHAT_DAILY_CAP = 30`, `coach-chat.ts:33`), both fail-closed, in addition to the per-actor AI quota above.
- **Pre-provider safety scan (for the current message):** `detectSafetyStop` (`src/lib/coach-chat.ts:87-93`) over pain/injury patterns (`coach-chat.ts` `PAIN_PATTERNS`) and disordered-eating/restriction patterns (`RESTRICTION_PATTERNS`); on a hit the route returns the bilingual refer-out copy (`COACH_CHAT_REFER_OUT`, `coach-chat.ts:94-…`) with `provider: 'safety'`, `model: null` at `route.ts:135-145` — **before** the provider call at `route.ts:161`, i.e. zero provider calls on a stop. Scope limitation is SEC-R1.
- **Output guardrail:** after truncation, `violatesCoachGuardrails(reply)` (`src/lib/coach-output.ts:110-112`: train/push-through-pain, skip-the-doctor, drug-directive patterns, plus sub-1200-kcal advice detection) triggers wholesale replacement with `COACH_SAFETY_FALLBACK` (`coach-output.ts:31-32`) and a `safetyFiltered: true` flag — applied at `route.ts:182-185`. The sibling coach route applies the stronger schema-validating form (`validateCoachOutput`, `coach-output.ts:146-…`) at `src/app/api/ai/coach/route.ts:273-…`.

### 4. Auth & account deletion (area 4)
- **Token construction/verification:** HMAC-SHA256 over the base64url payload, `del_<payload>.<signature>` format, 15-minute expiry, random-UUID `jti`, `purpose: 'account_deletion'` pinning — `src/lib/deletion-token.ts:90-124` (creation) and `:125-256` (verification), with `crypto.timingSafeEqual` after a length pre-check (`deletion-token.ts:157-166` approx.), expiry check, and email-match check returning `EMAIL_MISMATCH`.
- **SEC-19 (dedicated secret only):** `getSigningSecret` (`deletion-token.ts:61-68`) accepts **only** `SUPABASE_DELETION_SECRET` and throws otherwise — the old service-role/cron/`APP_SECRET` fallbacks are gone. Fail-closed in effect (see SEC-R4 for the error-shape caveat).
- **Replay protection:** in-memory `jti` map plus durable Supabase `consumed_deletion_nonces` ledger; `consumed` → `TOKEN_ALREADY_USED` (`deletion-token.ts:202-241`); `partial` deliberately re-usable so a 207 partial deletion can be retried to completion (line 236). Consume-on-success anonymizes `email`/`user_id` in the ledger (route's nonce block; `consumeDeletionNonce` in `deletion-token.ts:258-…`).
- **Route-level auth:** deletion requires either a Supabase-verified Bearer token (`supabase.auth.getUser`) or a valid verification token — an email alone never authorizes (`src/app/api/auth/delete-account/route.ts:291-345` approx.); a body email that mismatches the authenticated identity returns 403. In production, a missing service-role/admin client returns 503 `CONFIGURATION_ERROR` **before** any purge is attempted (`route.ts:240-258` approx.), closing the old anon-fallback partial-deletion path; the anon fallback in `getSupabaseServerClient` therefore cannot drive a production deletion. `request_verification` returns an identical 200 body whether or not the email matched (anti-enumeration), with a 500 ms timing-normalization delay on the unmatched path, and the debug-token payload is gated on `NODE_ENV === 'test'` **and** `ALLOW_DELETION_DEBUG_TOKEN === 'true'`. Rate limit 5/15 min/IP (`route.ts:109-114`); body cap 64 KB (`route.ts:128`). DB error strings are redacted before inclusion in responses (`route.ts:499-506`, `527-536`).

### 5. Headers / CSP (area 5)

Other directives are restrictive: `default-src 'self'`, `frame-ancestors 'none'`, `form-action 'self'`, `base-uri 'self'` (`next.config.js:70-82` approx.).

- **CSP-report sink sanity:** POST-only handler, rate-limited 60/min (`src/app/api/csp-report/route.ts:18-22`), streaming body cap 32 KB (`route.ts:26`), logs at most 2,000 redacted chars (`route.ts:28`), swallows all internal errors and returns 204 on the normal path (`route.ts:14-35`). Newline handling is SEC-R6.
