**Part 1 flags (missing/weak rate limiting or input caps):**
- **Only one route lacks a route-level rate limiter: #11 dispatch** — intentional and documented in-code, secret-authenticated, and still under the middleware 300/min/IP floor. Not a defect per se; its unbounded QStash-verify body read is filed as E2E-R7.
- **Fail-closed is AI-only.** #6, #7, #9, #10, #12, #13 call `checkRateLimit` without `failClosed`, so a limiter-backend outage silently degrades them to per-instance in-memory counts instead of 503 (E2E-R7). All five AI routes (#1–#5) fail closed.
- **No route is missing an input cap.** Every POST/DELETE body goes through a streaming capped reader (4 KB–16 MB by route); the only GET (#7) validates its sole parameter. `api-body-caps.test.ts` pins the non-AI caps (see Part 3).
- Error-shape inconsistency (cosmetic): #2 returns `{error}` with no `message`; most others return `{error, message}`; #9 returns nothing; #6 can return 207. Clients must special-case #2 — its own client does (`CoachChatSection.tsx` reads only `data.error`).

### Findings from Part 2 (detail; severities in the consolidated table)

- **Prompt-only trio.** Claims 3 and 4, and the citation half of claim 1, live entirely in `buildCoachChatSystemPrompt`. Nothing downstream verifies them. This is the honest characterization the coordinator asked for: the *context* is enforced by code; the *behavior rules* are instructions to a third-party model.
- **Safety scan scope.** `detectSafetyStop` runs on the current message only, with English regexes. A Hindi message such as "मेरे कंधे में दर्द है" (the refer-out copy itself uses दर्द / उल्टी) matches nothing and goes to the provider; pain disclosed in an earlier history turn or in a check-in note likewise never triggers the stop (notes are *sent to* the provider as context).
- **Safety sits behind the quotas.** Route order is minute-limit → shared quota → daily cap → body parse → safety scan. A user who has exhausted any cap and then reports pain receives 429/503, not the refer-out copy.

## Findings

| ID | Sev | Finding | Evidence |
|---|---|---|---|
| E2E-R1 | **P2** | Topic lock (claim 3), caution warnings (claim 4), and reply citation (claim 1) are **system-prompt strings with zero output-side enforcement** — no classifier, no reply scan for topic/caution/citation. A non-compliant provider reply is served as-is (unless it trips the narrow guardrail phrase list). Tests pin only the prompt text. | `coach-chat.ts:413-414`; `coach-output.ts:110-112` (guardrail scope); `tests/coach-chat.test.ts` prompt-substring tests |
| E2E-R2 | **P2** | Pre-provider safety scan covers **only the current message, only in English**. Hindi pain/restriction phrasing (e.g. दर्द, उल्टी — words the app's own Hindi refer-out uses) bypasses the stop and reaches the provider; pain disclosed in history turns or in today's check-in notes (which are forwarded as context) never triggers it. Hindi is a first-class UI language, so this is a real-population gap, not an exotic one. | `coach-chat.ts:56-90` (English-only regexes), `:87-90`; `route.ts:135` (scan input = `rawMessage` only); `CoachChatSection.tsx:202-205` + `coach-chat.ts:349-354` (notes → provider context) |
| E2E-R3 | P3 | Safety refer-out is **behind all three quota gates**: a user at the minute/shared/daily cap who reports pain gets 429 (or 503 on limiter outage) instead of the refer-out copy. Guests hit the shared 10/day quota quickly, making this reachable in normal use. | `route.ts:71,84,105` (limits) precede `:135` (safety scan) |
| E2E-R4 | P3 | History truncation keeps the **first** 10 turns, not the latest: `sanitizeHistory` breaks at the cap while iterating from the start, and the client's `messages` array grows unbounded, so (a) after 10 turns the model never sees recent exchanges, and (b) a long session eventually trips the 64 KB body cap and every further send fails with the generic error until reload. The route's `.slice(-COACH_CHAT_MAX_HISTORY_TURNS)` cannot recover the latest turns — the list is already truncated. | `coach-chat.ts:441` (`break` at cap); `route.ts` history line (`sanitizeHistory(...).slice(-10)`); `CoachChatSection.tsx` send() (full `messages` sent, no client slice) |
| E2E-R5 | P3 | The server **trusts client-supplied grounding**: `contextText`, `evidence`, and `hasData` are accepted from the request body (sliced/filtered only) with no binding to a server-verified user record, and the evidence array is echoed into the response — and rendered as "Based on your data" — whether or not the reply used it. Impact is bounded (local-first app; a client can only fabricate its *own* coach context, no cross-user data exists server-side), but "evidence cited" is therefore a display of client claims, not a server-verified citation. | `route.ts:127-130,189`; `CoachChatSection.tsx` evidence rendering |
| E2E-R6 | P3 | Per-muscle caution context is **dead in production wiring**: `CoachChatSection` always passes `perMuscle: []`, so the `MUSCLES NEEDING CAUTION TODAY` context section and its evidence never occur from the real UI, despite the lib supporting them and claim 4's "training while run-down" framing leaning on readiness data. (Readiness score/band *is* wired.) Documented in-code as a missing data source, not a bug of intent — but the shipped surface is narrower than the lib/tests suggest. | `CoachChatSection.tsx:128` (+ comment above it); `coach-chat.ts` per-muscle section (~:303-307) |
| E2E-R7 | P3 | Limiter posture is uneven outside the AI routes: barcode, feedback, delete-account, notifications preferences/subscribe, and csp-report rate-limit **without fail-closed** (limiter outage → silent per-instance in-memory degradation, vs the AI routes' 503); dispatch has **no route-level limiter and no body cap**, and its QStash verification reads the full request body via `req.clone().text()` with no size bound (mitigants: secret/QStash auth runs first for logic, middleware 300/min/IP floor applies, platform request-size limits may apply upstream — none verified here). | `rate-limit.ts:1-14`; route `checkRateLimit` calls without `failClosed` (Part 1 table); `notifications/dispatch/route.ts:72-79,141-145` |
| E2E-R8 | P3 | `dailyLeft` in the chat UI counts only the chat-specific 30/day cap, but the shared per-actor AI quota (guests: 10/day across **all** AI features) usually binds first — the UI can show "N messages left today" immediately before an `AI_QUOTA_EXCEEDED` 429, which the client maps to the generic "today's chat limit" copy. Counter and enforcement disagree. | `route.ts` success response (`dailyRemaining: daily.remaining`); `ai-quota.ts:61-62`; `CoachChatSection.tsx` 429 mapping + `dailyLeft` render |

## NOT TESTED — for the parent's live-browser stage

Everything below requires a running app / real provider / real device and was **not** exercised in this phase. Itemized for delegation:

1. **Guest chat grounded answer (live):** as a guest/fresh user with seeded local data (a logged workout, a PR, an active block), ask "what should I train today?" and verify the reply (a) names today's planned session **identically to the Home screen's Today card**, (b) cites real logged numbers, (c) renders the "Based on your data" evidence list under the reply.

3. **Topic-lock decline (live):** ask an off-topic question (e.g. a politics/news/coding question) and verify a one-line decline + redirect to training, with **no partial answer** — this is the live check for prompt-only claim 3 / E2E-R1.

5. **Safety message (live):** send "my knee hurts when I squat" and verify the refer-out copy renders (and, in Hindi UI, repeat with an English pain phrase); **also repeat with a Hindi pain phrase** ("मेरे घुटने में दर्द है") to confirm/refute the E2E-R2 bypass live.

9. **General live smoke (outside coach scope):** real push notification delivery to a device from a dispatch run; barcode scan via camera against a real product; meal scan with a real photo through the live vision cascade (incl. the Cloudflare stage) — all fixture/mocked in the suite.
10. **Real-database gate:** re-run `tests/security-integration-gate.test.ts` in an environment with Docker/Postgres available — its 20 tests (RLS isolation, deletion nonce replay, real route persistence) remain unverified, not failed on logic.
